01 / O caso da defesa

Qual problema estamos resolvendo?

A pessoa escolhe Feminino, Masculino ou Unisex no Espelho. As opções vêm da tabela TipoLook; a escolha continua disponível ao recarregar a página e acompanha o look salvo.

1. Ler do banco

A tela consulta um catálogo HTTP. O formulário não mantém uma lista fixa própria.

2. Persistir a escolha

O Espelho guarda o ID escolhido em mirror_states.tipo_look_id.

3. Mostrar em outra tela

Ao salvar, o esquema guarda a referência. Os detalhes do look exibem o nome vindo da API.

Ao terminar, você deve conseguir

  • Localizar o arquivo certo para mudar uma regra, um campo, uma consulta ou uma tela.
  • Explicar o caminho de uma requisição, do onChange até o COMMIT.
  • Testar a funcionalidade sem o frontend, usando Postman e SQL.
  • Distinguir falha de contrato, autenticação, configuração, migração e regra de negócio.
  • Modificar uma funcionalidade sem perder compatibilidade com dados antigos.
Requisito, aceitação e evidência

“Ter um select” é apenas uma parte. A evidência completa é: a lista veio do MySQL; a seleção foi gravada para o usuário autenticado; sobreviveu a um novo GET; o look salvo exibe o mesmo tipo em /schemes/{id}.

Pré-requisitos para a prática

Use um checkout do repositório, Java 21, Maven, Node e MySQL em um ambiente de desenvolvimento. Para as chamadas autenticadas, use uma conta de teste que já consiga entrar no aplicativo e tenha o e-mail confirmado para criar um Scheme. Tenha pelo menos duas peças no seu guarda-roupa para salvar um look. A aula pode ser lida sem nenhum desses serviços. O campo persistido estudado é o da página /mirror; a preferência de apresentação em /try-on não substitui esse fluxo de banco.

Vocabulário essencial antes de continuar

Backend: o servidor Java que valida regras e acessa os dados. Frontend: a interface Next.js que apresenta os dados. API: contrato HTTP entre os dois. DTO: objeto de entrada ou saída desse contrato. Entidade: objeto mapeado para o banco. FK: chave estrangeira que referencia uma linha de outra tabela. Transação: conjunto de operações que confirma ou desfaz suas mudanças como uma unidade.

03 / HTTP, JSON e segurança

A API estabelece o contrato.

Uma operação tem método, caminho, cabeçalhos, corpo e resposta. GET lê uma representação; PUT aqui altera o tipo escolhido; POST executa ações como vestir uma peça ou salvar um look. O caminho público da página e o caminho HTTP da API são coisas diferentes.

Página do navegador

/mirror
A interface Next.js carrega HTML e componentes React.

Recurso da API

/api/me/mirror
O Spring Boot devolve o estado do usuário em JSON.

Contrato da alteração de TipoLook
PUT {{apiBase}}/api/me/mirror/tipo-look
Authorization: Bearer {{accessToken}}
Content-Type: application/json
Accept: application/json

{
  "tipoLookId": "56000000-0000-4000-8000-000000000001"
}

O UUID identifica a linha escolhida. O corpo não precisa mandar nome, codigo nem userId. O nome vem do catálogo; o usuário é identificado pelo token validado pelo servidor.

Autenticação e autorização são verificações diferentes.

  • Autenticação: validar o JWT e identificar quem está fazendo a chamada.
  • Autorização: decidir se essa pessoa pode realizar a operação e acessar esse recurso.
  • Escopo do dado: em /api/me/..., usar CurrentUser para atuar sobre o Espelho da pessoa autenticada.

O backend valida JWT RS256. Papéis do token são usados pelas regras de segurança; rotas /api/admin/** exigem ADMIN. GET /api/tipos-look não está na lista de GETs públicos: exige autenticação, mesmo sendo uma leitura de catálogo.

O select desabilitado não é uma regra de segurança

Qualquer cliente pode enviar HTTP, inclusive Postman. O backend deve validar o formato do ID, confirmar que ele existe e usar a identidade autenticada. A UI ajuda a pessoa; o servidor decide se a mudança é válida.

04 / O dado no MySQL

Uma tabela de catálogo, duas referências.

TipoLook contém as opções. mirror_states guarda a seleção atual. schemes guarda o tipo associado ao look salvo. Cada FK impede que o banco aceite uma referência a um tipo inexistente.

TipoLook

  • PK id : CHAR(36)
  • UNIQUE codigo : VARCHAR(30)
  • nome : VARCHAR(80)
  • created_at / updated_at

mirror_states

  • PK id
  • UNIQUE user_id
  • FK tipo_look_id → TipoLook.id
  • slots_json

schemes

  • PK id
  • FK user_id
  • FK tipo_look_id → TipoLook.id
  • title / origin / …

Um TipoLook pode ser referenciado por muitos Espelhos e muitos looks. Cada registro guarda zero ou um tipo.

mirror_states.tipo_look_id…
schemes.tipo_look_idNenhum look salvo nesta simulação

Escolha um tipo, salve e depois altere o Espelho. Compare as duas referências.

O que realmente é preservado quando você salva?

O look recebe sua própria referência a TipoLook. Mudar a seleção do Espelho depois não altera essa FK do look. Entretanto, o nome continua sendo consultado na linha de catálogo: renomear TipoLook.nome muda o rótulo exibido por todas as referências desse tipo. É uma preservação da seleção do tipo, não uma cópia imutável do texto do catálogo.

Por que as novas colunas aceitam NULL?

Looks e Espelhos anteriores à funcionalidade não tinham uma seleção. A migração preserva NULL nesses registros, sem atribuir um gênero que a pessoa não escolheu. A tela trata a ausência, e uma nova seleção válida passa a ser persistida.

SQL de leitura — use IDs obtidos no seu ambiente
SELECT id, codigo, nome
FROM TipoLook
ORDER BY nome;

SELECT m.user_id, m.tipo_look_id, t.codigo, t.nome
FROM mirror_states m
LEFT JOIN TipoLook t ON t.id = m.tipo_look_id
WHERE m.user_id = '<UUID_DO_USUARIO_DE_TESTE>';

SELECT s.id, s.title, s.tipo_look_id, t.codigo, t.nome
FROM schemes s
LEFT JOIN TipoLook t ON t.id = s.tipo_look_id
WHERE s.id = '<SCHEME_ID_RETORNADO_PELA_API>';
Capitalização e migração importam

O nome da tabela é TipoLook. Em ambientes MySQL com nomes de tabela sensíveis a maiúsculas, tipolook não é o mesmo nome. A configuração usa Flyway e ddl-auto: none: criar só uma classe Java não cria a tabela.

05 / Controller, DTO e JPA

Como o contrato vira código Java?

A entidade descreve os dados persistidos.

TipoLook.java — trecho real, imports omitidos
@Getter
@Setter
@NoArgsConstructor
@Entity
@Table(name = "`TipoLook`")
public class TipoLook extends AuditableEntity {
    @Column(nullable = false, unique = true, length = 30)
    private String codigo;

    @Column(nullable = false, length = 80)
    private String nome;
}

@Entity registra a classe no JPA. @Table define o nome da tabela. A classe base AuditableEntity fornece UUID, datas e autores de criação/alteração. Lombok gera métodos como getNome(), reduzindo código repetitivo; ele não gera a tabela.

MirrorState.java e Scheme.java — associação presente nas duas entidades
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "tipo_look_id")
private TipoLook tipoLook;

ManyToOne expressa que vários Espelhos ou esquemas podem apontar para o mesmo tipo. LAZY adia o carregamento da associação. A FK guarda o ID; o objeto Java representa a relação.

O repository fornece consultas e persistência.

TipoLookRepository.java — trecho real
public interface TipoLookRepository
        extends JpaRepository<TipoLook, UUID> {
    List<TipoLook> findAllByOrderByNomeAsc();
}

O Spring Data fornece a implementação. O nome findAllByOrderByNomeAsc deriva uma consulta que ordena pelo campo nome. Métodos como findById e save vêm de JpaRepository. Não é necessário escrever SQL manual para essa consulta simples.

O controller lista o catálogo.

TipoLookController.java — método real
@GetMapping("/api/tipos-look")
@Transactional(readOnly = true)
public List<Views.TipoLookView> tiposLook() {
    return tipos.findAllByOrderByNomeAsc()
            .stream().map(Views::tipoLook).toList();
}

A resposta é uma lista de TipoLookView, não o grafo completo de entidades JPA. O record de saída expõe apenas id, codigo e nome. Essa separação evita acoplar o consumidor aos campos internos de auditoria ou a associações da entidade.

O DTO de entrada valida o campo escolhido.

MirrorController.java — trecho real, annotation de documentação omitida
@RequestMapping("/api/me/mirror")
// ...
public record TipoLookRequest(@NotNull UUID tipoLookId) { }

@PutMapping("/tipo-look")
public Map<String, Object> tipoLook(
        CurrentUser user,
        @jakarta.validation.Valid @RequestBody TipoLookRequest body) {
    return mirror.updateTipoLook(user, body.tipoLookId());
}

A rota final concatena o prefixo da classe e o sufixo do método. Jackson converte JSON em um record Java. @NotNull exige o campo, e @Valid dispara essa validação. Um UUID válido sintaticamente ainda pode não existir: a regra de existência fica no service.

Qual a diferença entre DTO, entidade e View?

TipoLookRequest é o DTO de entrada: “o cliente quer selecionar este ID”. TipoLook é a entidade persistida: “esta opção existe no catálogo”. TipoLookView é o DTO de saída: “estes são os dados que a tela precisa mostrar”. Separá-los permite evoluir cada responsabilidade e impede o cliente de editar qualquer propriedade de uma entidade enviando JSON arbitrário.

Fontes: TipoLook.java · TipoLookRepository.java · MirrorController.java · Views.java

06 / Regras e transações

O service decide o que pode ser salvo.

MirrorService.updateTipoLook — método real
@Transactional
public Map<String, Object> updateTipoLook(CurrentUser user, UUID tipoLookId) {
    if (tipoLookId == null)
        throw ApiException.badRequest("TIPO_LOOK_INVALIDO",
                Msg.t("mirror.tipo_look_invalido"));

    var tipo = tiposLook.findById(tipoLookId)
            .orElseThrow(() -> ApiException.badRequest("TIPO_LOOK_INVALIDO",
                    Msg.t("mirror.tipo_look_invalido")));

    MirrorState state = stateEntity(user.id());
    state.setTipoLook(tipo);
    mirrors.save(state);
    return render(user, state, slots(state), Map.of());
}
  1. Protege contra um ID nulo, inclusive em chamadas Java sem controller.
  2. Busca o tipo e rejeita um ID inexistente.
  3. Obtém o Espelho do usuário autenticado.
  4. Altera a referência da entidade e persiste seu estado.
  5. Monta a resposta que a tela utilizará para atualizar a seleção.

O que @Transactional oferece?

O Spring abre uma transação quando o método é chamado pelo proxy do service. O JPA acompanha as entidades alteradas e sincroniza as mudanças com o banco. Quando a operação termina com sucesso, a transação confirma; uma exceção de runtime pode provocar rollback. Chamar save não equivale, por si só, a já ter um commit independente.

O backend configura open-in-view: false. Por isso, relações lazy devem ser lidas e transformadas em DTO enquanto houver o contexto apropriado de transação. O retorno Views.tipoLook(...) produz dados simples para o JSON.

Camadas evitam duplicação de regra

O botão da tela e o Postman chegam ao mesmo MirrorService. A regra “o tipo deve existir” funciona para ambos. Não dependa apenas de o select listar opções corretas.

Salvar o Espelho como Scheme é um segundo caso de uso.

POST /api/me/mirror/save chama o fluxo de materialização. Ele exige pelo menos duas peças; o erro é 400 SEM_PECAS quando essa condição não é atendida. Um esquema já existente pode ser reutilizado quando pertence ao usuário e contém as mesmas peças e o mesmo TipoLook.

MirrorService.materialize — linhas centrais, trecho abreviado
// ... valida peças e cria o Scheme pelo SchemeService ...
Scheme scheme = schemes.findById(view.id()).orElseThrow();
scheme.setTipoLook(mirror.getTipoLook());
return schemes.save(scheme);

A deduplicação também considera o ID do tipo. Sem isso, salvar as mesmas peças com uma seleção diferente poderia devolver um esquema antigo com outro tipo. A seleção é parte da identidade do look salvo nessa operação.

O que dizer se a banca perguntar “onde está a regra?”

A estrutura e o formato do request são verificados pelo DTO/controller; a existência da opção e o uso do Espelho autenticado são tratados no service; a integridade relacional é protegida pela FK no banco. Essas verificações se complementam.

Fonte: MirrorService.java — updateTipoLook, findExistingScheme, materialize, save.

O estado devolvido pela API é usado para atualizar a página. Em um novo carregamento, GET /api/me/mirror devolve o tipoLook persistido; o valor do select é restaurado pelo ID. A mensagem e o rótulo do campo passam pelo sistema de traduções do projeto.

Qual é o papel de API_BASE?

NEXT_PUBLIC_API_BASE_URL define a base da API usada pelo cliente. Para requests normais, o cliente executa fetch(API_BASE + path), envia JSON e inclui Authorization: Bearer .... Por ser uma variável NEXT_PUBLIC_..., ela é incorporada ao build do frontend: trocar a variável após um deploy exige gerar e publicar o novo build.

Exemplo de configuração local — valores de desenvolvimento
# Frontend: arquivo .env.local na raiz
NEXT_PUBLIC_API_BASE_URL=http://localhost:8080

# Backend: permitir a origem local do frontend
APP_CORS_ALLOWED_ORIGINS=http://localhost:3000

O BFF participa da autenticação, não de toda chamada de negócio.

As operações de login, cadastro, refresh e logout têm rotas Next em /bff/auth/*. O BFF mantém o refresh token em cookie HttpOnly; o access token dura 15 minutos e fica na memória da aba. O cliente tenta renovar a sessão quando necessário e pode repetir uma chamada após 401. A seleção de TipoLook vai diretamente à API Java com o access token.

Fluxo de negócio

Navegador → API Spring Boot
PUT /api/me/mirror/tipo-look
Bearer JWT no cabeçalho

Renovação da sessão

Navegador → BFF Next → API
POST /bff/auth/refresh
Refresh em cookie HttpOnly

CORS e autenticação resolvem problemas diferentes

CORS permite ou impede que o navegador leia uma resposta de outra origem. JWT identifica o usuário. Uma chamada funcionar no Postman e falhar no navegador é uma pista para verificar CORS, base URL e gate; Postman não aplica a política CORS do navegador.

Em qual outra página o dado aparece?

O botão de salvar envia POST /api/me/mirror/save e usa o schemeId retornado para abrir /schemes/{id}. Essa página consulta GET /api/schemes/{id}. O envelope contém scheme.tipoLook, e components/scheme-card.tsx renderiza tipoLook.nome quando a referência existe.

SchemeCard — apresentação do tipo persistido

  <p>{t("lookType.label")}: {scheme.tipoLook.nome}</p>

09 / Testar no Postman

Teste a API sem depender da interface.

Crie um ambiente de teste no Postman com apiBase (por exemplo, http://localhost:8080), accessToken, tipoLookId, pieceId1, pieceId2 e schemeId. Use valores do seu ambiente. Os UUIDs do catálogo abaixo vêm da migração V56; os IDs de peças e usuário devem vir da sua conta de teste.

1. Entrar e guardar o access token.

POST {{apiBase}}/api/auth/login — conta de desenvolvimento
{
  "identifier": "<USUARIO_OU_EMAIL_DE_TESTE>",
  "password": "<SENHA_DA_CONTA_DE_TESTE>",
  "rememberMe": false,
  "deviceName": "Postman"
}

Configure o corpo como raw → JSON e Content-Type: application/json. A resposta de login contém accessToken, refreshToken, informações de expiração e usuário. No Postman, você chama a API diretamente; não precisa reproduzir o cookie HttpOnly do BFF para testar os endpoints de negócio com Bearer.

Post-response script do login — apenas no ambiente local de teste
pm.test("Login respondeu com sucesso", () => {
  pm.response.to.have.status(200);
});
const body = pm.response.json();
pm.environment.set("accessToken", body.accessToken);

Não coloque credenciais nem tokens em arquivos versionados ou exportações compartilhadas da coleção. Configure a autorização da coleção como Bearer {{accessToken}}.

2. Executar a sequência do caso TipoLook.

O catálogo é ordenado por nome. Não dependa de o primeiro registro ser Feminino: selecione pelo codigo ou ID. O endpoint de peças exige uma peça acessível à conta; trocar uma peça do mesmo slot pode substituir a anterior e deixar apenas uma peça no Espelho. Para salvar um Scheme, a conta também precisa ter o e-mail confirmado: essa regra é verificada por Guard.requireCanCreate no SchemeService. A seleção de TipoLook, isoladamente, exige autenticação.

Se precisar do UUID da pessoa para a consulta SQL, leia GET /api/me autenticado. Não altere o request de TipoLook para aceitar um userId informado pelo cliente.

3. Confirmar que alterações posteriores não mudam o look anterior.

  1. Anote o tipo e o ID do Scheme salvo.
  2. Faça PUT no Espelho escolhendo outro ID do catálogo.
  3. Leia novamente GET /api/me/mirror: deve mostrar o tipo novo.
  4. Leia o Scheme anterior: deve continuar com a seleção anterior.
  5. Salve as mesmas peças com o novo tipo e compare os IDs; a deduplicação não deve reaproveitar um Scheme de tipo diferente.

4. Exercitar falhas previsíveis.

Envie {} e espere 422 VALIDACAO; envie {"tipoLookId":"abc"} e espere 400 JSON_INVALIDO; envie um UUID ausente da tabela e espere 400 TIPO_LOOK_INVALIDO. Remova o Bearer para verificar a autenticação. Depois dessas falhas, faça GET e confirme que a seleção válida anterior não foi substituída.

Como encontrar os IDs das peças da conta?

Use o aplicativo e a aba Network do navegador para observar a lista do guarda-roupa ou as peças já vestidas retornadas pelo Espelho. O endpoint GET /api/me/mirror/wardrobe?slot=... também permite selecionar peças para um slot; use o valor de slot real enviado pela tela. Não use IDs de produto do catálogo no lugar de IDs de peças do seu guarda-roupa.

11 / Provar com testes

Que evidência cada teste fornece?

Um teste de service verifica regras sem exigir o navegador. Um teste de UI verifica a interação com respostas HTTP simuladas. Um roteiro API + SQL verifica a aplicação rodando e a persistência real. Eles são complementares; mocks de repository não comprovam que uma migration foi aplicada no MySQL.

Como melhorar um teste sem copiar a implementação?

Teste o comportamento observável: “depois de salvar Feminino e mudar o Espelho para Masculino, o primeiro Scheme continua Feminino”. Esse cenário detecta uma FK copiada incorretamente ou uma deduplicação sem o tipo. Um teste que apenas verifica que um setter foi chamado oferece uma prova menor.

Desafio de teste: qual cenário falta em um novo campo de descrição?

Verifique catálogo com descrição e com NULL; o select continua selecionando por ID; a descrição aparece quando o tipo é selecionado; dados antigos sem descrição não quebram o card ou formulário. Se a descrição for opcional, não torne o antigo payload inválido por acidente.
