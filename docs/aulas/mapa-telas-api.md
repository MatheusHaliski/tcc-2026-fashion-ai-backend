# Mapa de telas e API do FashionAI

O frontend Next.js contém as telas do produto e os painéis administrativos. O backend Spring Boot oferece controllers REST e serviços: não existe uma segunda tela Java correspondente a cada página. A coluna **Função backend/API** indica a operação que atende a ação da tela.

Este mapa cruza as páginas `app/`, seus componentes e as anotações de rota dos controllers em `fai-web`. Mostra operações centrais de cada fluxo; não é um inventário de todos os endpoints nem de todas as chamadas auxiliares de cada componente. Laboratórios e o gate técnico de desenvolvimento foram excluídos. Os arquivos são caminhos relativos à raiz do repositório. `{id}`, `{username}`, `{slug}` e demais valores entre chaves são parâmetros que precisam ser substituídos no teste.

As rotas `/api/...` usam a origem definida em `NEXT_PUBLIC_API_BASE_URL` (localmente, `http://localhost:8080`). Login e cadastro passam por `POST /bff/auth/login` e `POST /bff/auth/register` no Next, que encaminha a chamada aos endpoints Java indicados na tabela. As rotas protegidas da API usam `Authorization: Bearer <accessToken>`; não cole tokens reais na documentação. Uploads como peça, foto, Lens e Avatar usam `multipart/form-data`, conforme o controller.

## Exemplo para a defesa: TipoLook no Espelho

1. `GET /api/tipos-look` consulta `TipoLookRepository.findAllByOrderByNomeAsc()` e entrega as opções do banco para o campo no Espelho.
2. A escolha envia `PUT /api/me/mirror/tipo-look` com JSON `{"tipoLookId":"<UUID retornado pela consulta>"}`. `MirrorService.updateTipoLook` valida a chave e grava a referência em `MirrorState`.
3. `GET /api/me/mirror` devolve o `tipoLook` salvo. Com ao menos duas peças vestidas no Espelho, `POST /api/me/mirror/save` copia essa referência para o `Scheme` criado. Sem peças suficientes, o serviço responde com validação; não basta selecionar o tipo para criar um look.
4. `GET /api/me/schemes` devolve os looks para `/looks`; `components/scheme-card.tsx` exibe `scheme.tipoLook.nome`. Assim o dado cadastrado no Espelho aparece em outra página.

Arquivos do exemplo: [TipoLook.java](../../fai-domain/src/main/java/br/com/fashionai/domain/model/TipoLook.java), [MirrorState.java](../../fai-domain/src/main/java/br/com/fashionai/domain/model/MirrorState.java), [Scheme.java](../../fai-domain/src/main/java/br/com/fashionai/domain/model/Scheme.java), [Views.java](../../fai-application/src/main/java/br/com/fashionai/application/view/Views.java) e [migração V56](../../fai-infrastructure/persistence-mysql/src/main/resources/db/migration/V56__tipo_look_no_espelho.sql).

## Como ler os redirecionamentos e as abas

`/` leva a `/feed`. `/lookbook` leva ao próprio `/u/{username}` e conserva a aba solicitada. `/dashboard` é um atalho: contas comuns seguem para o Lookbook; marcas e celebridades seguem para o perfil institucional, com `tab=METRICAS` depois da aprovação ou `tab=CENTRAL` enquanto o pedido é acompanhado. Não são três dashboards independentes.

Abas como selos, promoções, vitrine, Flair e criador de guarda-roupa compartilham `/brands/{slug}` e são implementadas por componentes diferentes. A administração global continua em `/admin/*`, no frontend, com autorização exigida pelos controllers Java. A disponibilidade de uma aba depende do tipo de conta, de ser dono do perfil e das regras de acesso.

A formação do Avatar 3D (análise, atlas, geometria e renderização) ocorre principalmente no navegador. `Avatar3dController` recebe, versiona e devolve os artefatos; a tabela não atribui ao Java a renderização Three.js. No Provador, a página atual consulta o estado e o catálogo e monta a prévia no navegador; os endpoints adicionais de renderização existentes em `TryOnController` não foram listados como chamadas de botões que esta página não faz.
